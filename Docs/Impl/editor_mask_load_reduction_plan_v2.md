# SpecularExV2 エディタ負荷対策 v2（保証範囲をシーンに限定する再設計）

作成日: 2026-09-27  
対象リビジョン: `dfbb2e8`（v1 の M・A・B・C・D・E・F・G・H 実装済み）  
前提文書: `editor_mask_load_reduction_plan.md`（以下 v1）  
対象ファイル: `Editor/SpecularExPackedMaskWatcher.cs`、`Editor/SpecularExPackedMaskStore.cs`、`Editor/SpecularExV2Inspector.cs`、`Editor/Language/*.json`

## 1. 目的と設計思想の変更

v1 は「ユーザーにマスクパッキングを一切意識させない」ことを前提にしていた。そのため、**プロジェクト内のすべての SpecularEx マテリアル** を常に正しい状態に保とうとし、次の仕組みが必要になった。

- 逆依存インデックス（F）。未構築時・復元失敗時にはプロジェクト全体の走査が起きる
- ドメインリロードをまたいで未処理キュー・監視記録・インデックスを `SessionState` に保存・復元する仕組み（C）
- 状態を失ったときの全件確認（`_fullCheckReason`）
- 自己保存の抑制（B）

v2 では保証範囲を狭め、その代わりに手動修復の導線を目立たせる。

| 項目 | v1 | v2 |
|---|---|---|
| ツールが自動で正しさを保証する範囲 | プロジェクト内の全 SpecularEx マテリアル | **ロード中のシーンと Prefab Stage 上の Renderer が使うマテリアル**、および Inspector で表示中のマテリアル |
| 非アクティブなオブジェクト | アクティブなものと同じ優先度で即時検証 | シーン走査では **検証を後回し**（監視登録のみ）。アクティブ化・Inspector 表示・ユーザー操作・ビルド時に検証 |
| 範囲外のマテリアル（シーンにない `.mat` など） | 依存インデックス経由で追従 | 追従しない。シーンに置かれる、Inspector で開く、再ベイク、ビルドのいずれかで修復 |
| 不整合時の修復手段 | 折りたたみの中の「パック済みマスクを再ベイク」ボタン（既定は閉じている） | **常時表示のステータス行とワンクリック修復**。Hierarchy の右クリックとメニューからも修復できる |
| プロジェクト全体の走査 | 初回のテクスチャイベント、削除時のフォールバック、状態喪失時に自動で発生 | **自動では発生しない**。明示的なメニュー（Update All Materials / Delete Unused）でのみ行う |

ユーザーが目で見て確認できるのは、シーン上の、アクティブなオブジェクトだけである。そこが常に正しく、それ以外は「使うとき」か「ビルド時」に直る、という保証で十分だと考える。見えない場所を常に正しく保つためのコストを払わないことで、処理とコードの両方を単純にする。

### 1.1 変えないもの

- **ビルドの正しさ。** VRCSDK フック（`SpecularExPackedMaskBuildHook`）と NDMF プラグインは、アバターの Renderer とアニメーションが参照するマテリアルをすべて集め、`useCache: false` で `EnsureAll` を呼ぶ。これは Watcher の保証範囲と独立しているため、非アクティブなオブジェクトやアニメーションで差し替えるマテリアルもアップロード時には必ず正しくなる。v2 はこの経路に手を入れない。
- **ストアのモデル。** 内容アドレス方式のファイル名、`EnsureAll` の冪等性、インポート設定を importer に直接書く方式（`OnPreprocessTexture` を使わない）は維持する。
- v1 の A（スロット状態による絞り込み）、D（インポート設定確認のキャッシュ）、E（シェーダーフォルダーのキャッシュ）、G（Inspector 状態のキャッシュ）、H（検証済みマテリアルのキャッシュ）、M（計測）。
- v1 の I（`.meta` を先に書いてインポートを1回にする）は v2 と独立しているため、引き続き検証待ちの項目として扱う。

## 2. v1 実装で残っている負荷と複雑さ

v1 実装（`dfbb2e8`）を読み直して、次の点を確認した。

| # | 箇所 | 内容 | 根拠 |
|---|---|---|---|
| 1 | 依存インデックスの構築 | 最初のテクスチャイベントで `FindAssets("t:Material")` と全コンテナの `GetDependencies` を行う。プロジェクトの規模に比例し、関係ないテクスチャの保存でも初回は必ず走る | Watcher `251–259, 358–386` |
| 2 | 全件確認 | インデックス構築前の削除、状態の復元失敗、`SessionState` のサイズ超過で、**全 SpecularEx コンテナをロード** し、検証キャッシュも捨てる | Watcher `227–250, 611–615` |
| 3 | コンテナのインポート | `.mat` / `.asset` / モデルのインポートごとに `GetDependencies` を取る。Modular Avatar などの `.asset` 保存でも走る。SpecularEx を使うファイルはロードする | Watcher `278–291` |
| 4 | ドメインリロード | インデックス・監視記録・キューを JSON にして `SessionState` に保存・復元する。リロード後は全シーンマテリアル（非アクティブを含む）を検証キャッシュなしで検証する | Watcher `506–645, 296–303` |

| 6 | 修復導線 | 再ベイクボタンは「マスクパッキング状態」の折りたたみの中にあり、折りたたみは既定で閉じている。ユーザーが存在に気づきにくい | Inspector `147, 1007–1045` |

1〜5 はすべて「プロジェクト全体を正しく保つ」ための仕組みである。保証範囲をシーンに限定すれば、1・2・4 は不要になり、3・5 はごく小さな処理で済む。Watcher は約 760 行から約 300 行に減る見込み。

## 3. v2 の設計

### 3.1 保証範囲（スコープ）

Watcher が扱うマテリアルを **監視セット** と呼ぶ。監視セットは次の3つの和集合である。

1. **シーン由来:** ロード中の全シーンと現在の Prefab Stage にある Renderer（非アクティブを含む）の `sharedMaterials`
2. **操作由来:** Inspector で表示したマテリアル、変更イベント（スロット変更・Renderer の変更・オブジェクト生成）で要求されたマテリアル
3. 上記のうち、まだ監視セットから外していないもの（多めに含む分には正しさに影響しない。次のシーン再走査で整理する）

監視セットの各マテリアルは次のどちらかの状態を持つ。

| 状態 | 意味 | 入る条件 |
|---|---|---|
| **検証済み**（verified） | 最後の検証が成功し、H のキャッシュに載っている | アクティブな Renderer で使われている、または操作由来で要求された |
| **保留**（deferred） | 監視記録（参照パス）は持つが、検証はまだしていない | シーン走査で見つかり、使われている Renderer がすべて非アクティブ |

「アクティブ」の定義は `renderer.enabled && renderer.gameObject.activeInHierarchy`。1つでもアクティブな Renderer で使われていればアクティブとして扱う。

**不変条件:** `_slotState`（A）と `_verified`（H）に載るマテリアルは、必ず監視セットに含まれる。監視セットから外すときは両方から同時に消す。これにより、監視していない間にソースが変わったマテリアルが古いキャッシュのまま「検証済み」と扱われることを防ぐ。監視セットに戻ってきたときは初めて見るマテリアルとして検証される。

### 3.2 トリガーと処理

| トリガー | v2 の処理 | 優先度 |
|---|---|---|
| ドメインリロード、シーンを開く・閉じる、Prefab Stage を開く・閉じる | シーン再走査（3.3） | アクティブ: 即時検証、非アクティブ: 保留 |
| Inspector の描画 | `RequestIfSlotsChanged`（v1 と同じ） | 即時 |
| マテリアルのプロパティ変更、Renderer の変更、オブジェクト生成 | `RequestIfSlotsChanged`（v1 と同じ）。非アクティブでも即時に扱う | 即時 |
| GameObject のプロパティ変更（**アクティブ化**） | 新規。対象の GameObject が `activeInHierarchy` なら、配下のアクティブな Renderer が使う **保留中のマテリアルだけ** を要求する | 即時 |
| テクスチャ（ソース・生成マスク）のインポートと削除 | 監視セットのパス逆引き（`_byPath`）で当たったマテリアルだけを対象にする。検証済みなら H を無効化して要求、保留ならそのまま（アクティブ化時に検証される） | 即時 |
| コンテナ（`.mat` / `.asset` / モデル）のインポート | **監視セットに同じパスのマテリアルがある場合だけ** `RequestIfSlotsChanged`。それ以外は何もしない（`GetDependencies` も呼ばない） | 即時 |
| コンテナの削除 | 何もしない（破棄されたマテリアルは次の処理で監視セットから落ちる） | — |
| 移動 | 監視記録のパスを書き換える（v1 の `MoveTrackedPath` と同じ）。インポート設定キャッシュの無効化も維持 | — |
| ビルド（VRCSDK / NDMF） | 変更なし。Watcher を通らず `useCache: false` で全検証 | — |

ポイント:

- **ユーザー操作が起点のものは即時、シーン走査が起点のものだけを優先度で分ける。** 非アクティブな衣装のマテリアルをユーザーが直接差し替えた場合などは、その1件だけなのですぐ検証する。
- **テクスチャイベントの処理はハッシュ表の参照だけで済む。** 関係ないテクスチャの保存では、ロードも依存関係の取得も起きない。
- **自己保存の抑制（v1 の B）は廃止する。** 自分で保存した `.mat` の再インポートは「監視セットにあるコンテナのインポート」として届くが、スロットの参照は保存時点から変わっていないため `RequestIfSlotsChanged` が比較だけで終わる。v1 でコンテナのインポートに H の無効化をかけていた（Watcher `294`）のは、プロジェクト全体から集めた対象を信用できなかったためで、v2 では不要になる。外部ツールで `.mat` が書き換えられた場合は、スロット参照が変わっていれば検出できる。

### 3.3 シーン再走査

```
RescanScenes():
    newSet = {}
    for each Renderer r in loaded scenes + prefab stage (includeInactive: true):
        active = r.enabled && r.gameObject.activeInHierarchy
        for each SpecularEx material m in r.sharedMaterials:
            newSet[m] |= active
    for each material in tracked but not in newSet and not requested by user this session:
        Untrack(m)   // _tracked, _byPath, _slotState, _verified から同時に削除
    for each (m, active) in newSet:
        Track(m)     // 参照パスの記録のみ（GetTexture と GetAssetPath）
        if active: targets.Add(m)       // H のキャッシュが有効なら比較だけで終わる
        else:      _deferred.Add(m)
```

- ドメインリロード直後は H が空なので、アクティブなマテリアルは全件検証になる。v1 は非アクティブを含むシーン全マテリアルを検証していたので、その分だけ減る。
- **`SessionState` への保存・復元は廃止する。** 保証範囲がシーンだけなら、リロード後の再走査と検証（`InputKey` に依存ハッシュが入るため、リロード中に変わったソースも検出できる）で状態を完全に作り直せる。リロード前に届いていた未処理イベントが失われても、その対象がシーン上にあれば再検証で拾え、シーン外なら元々保証範囲外である。
- 監視セットから外す判定の「このセッションでユーザーが要求したもの」は、Inspector で開いたままのプロジェクト `.mat` を毎回外して検証し直すことを防ぐためのもの。単純さを優先するなら、外してしまい、次の OnGUI で再要求させてもよい（検証1回分のコストで済む）。**推奨は後者（区別しない）。**

### 3.4 非アクティブの扱い

保留中のマテリアルが検証されるのは次のとき。

1. アクティブ化の変更イベント（3.2）
2. Inspector で表示したとき
3. 手動の修復・再ベイク（3.6）
4. ビルド（Watcher とは独立）

保留中のマテリアルは Scene ビューにも Game ビューにも描画されないため、古いパック参照のままでも見た目に影響しない。アクティブ化のイベントが届かない経路（スクリプトが Undo を記録せずに `SetActive` を呼ぶ場合、Animation ウィンドウのプレビューなど）では、表示されても古い状態のままになり得る。ここは **ステータス表示と再ベイク導線で補う範囲** とする。

アイドル時に保留分を少しずつ検証する処理（`EditorApplication.update` で1フレームに数件など）も考えられるが、v2 では入れない。複雑さに見合う利点がないため。計測で必要と分かった場合に検討する（7章）。

### 3.5 コンテナ・テクスチャのインポートの流れ

```
Postprocessor.OnPostprocessAllAssets(imported, deleted, moved, movedFrom):
    NoteAssetChange()                         // G のアセット世代（v1 と同じ）
    for path in imported + deleted:
        if IsGeneratedPath(path): InvalidateImportSettings(path)        // D（v1 と同じ）
        if _byPath.TryGetValue(path, out ids): _dirtyIds.UnionWith(ids) // 逆引きのみ
    for moved: パスの書き換えと D の無効化（v1 と同じ）
    if _dirtyIds.Count > 0: Schedule()

Process():
    for id in _dirtyIds:
        m = _tracked[id].material
        if m == null or not HasPackedSlot(m): Untrack(id); continue
        if _deferred.Contains(m): continue           // 保留中はアクティブ化まで待つ
        InvalidateVerified(m); targets.Add(m)
```

`_byPath` にはソーススロット・パック先スロット・マテリアル自身のアセットパスを登録する。コンテナのインポートとテクスチャのインポートを区別する必要がなくなり、拡張子のテーブル（`TextureExtensions` / `MaterialContainerExtensions`）も Watcher からは不要になる。コンテナのインポートで当たった場合、H を無効化せずに `RequestIfSlotsChanged` にするかは実装時に決める。単純さを優先するなら、どちらも H を無効化して検証してよい（監視セットのマテリアルだけなので件数は少ない）。

### 3.6 修復導線（アクセス性の向上）

保証範囲を狭めた分、「おかしいと思ったらすぐ直せる」ことを設計の一部とする。

#### Inspector: 常時表示のステータス行

- SpecularExV2 Inspector の上部（バージョンバーの直下）に、折りたたみとは別に1行のステータスを常に表示する。
  - 最新・マスク未設定: 控えめな表示（例: `パック済みマスク: 最新`）と小さな「再ベイク」ボタン
  - 更新待ち・保存されていないテクスチャを含む: 警告色の表示と「再ベイク」ボタン
- 複数選択時は状態を集約して1行にする（最も悪い状態を表示する）。
- `GetState` は G でキャッシュされているため、毎回の OnGUI で呼んでも負荷は小さい。キャッシュが外れたときのコストは `InputKey`（ソース最大8枚の依存ハッシュ）程度。
- 既存の折りたたみ「マスクパッキング状態」は詳細表示（フィンガープリント・パック済みテクスチャ）として残す。ボタンは上部に移したので、折りたたみ内のボタンは削除してよい。
- `pack_pending` の文言を「更新待ち (自動でベイクされます)」から、手動修復もできることが分かる文言に変える（例: 「更新待ち — 直らない場合は再ベイクしてください」）。

#### シーン・アバター単位のワンクリック修復

| 導線 | 対象 | 処理 |
|---|---|---|
| Hierarchy の右クリック `SpecularExV2/パック済みマスクを修復` | 選択した GameObject の配下（非アクティブを含む）の Renderer が使うマテリアル。Animator のコントローラーのクリップが参照するマテリアルも含める | 修復（下記） |
| メニュー `Window/SpecularExV2/Packed Masks/Repair Scene Materials` | ロード中の全シーンと Prefab Stage（非アクティブを含む） | 修復 |
| Project ウィンドウの右クリック `SpecularExV2/Rebake Packed Masks` | 選択したマテリアル | 再ベイク |
| Inspector の「再ベイク」ボタン | Inspector の対象マテリアル | 再ベイク（現行と同じ） |
| メニュー `Update All Materials`（既存） | プロジェクト全体 | 修復。v2 ではインデックスを作らず、`FindMaterialContainerPaths` の走査だけにする |

「修復」と「再ベイク」は分ける。

- **修復**: `EnsureAll(targets, persist: true, useCache: false)`。H・D のキャッシュを迂回して参照・ファイルの存在・インポート設定をすべて確認し、ずれているものだけ直す。既存の PNG を書き直さないので、件数が多くても速い。対象は監視セットにも登録し直す（非アクティブも含めて検証済みになる）。
- **再ベイク**: `EnsureAll(targets, persist: true, rebake: true)`。PNG を作り直し、再インポートと圧縮を行う。2048² の BC7 圧縮は1枚数秒かかり得るため、対象を絞った操作（Inspector・マテリアル選択）にだけ割り当てる。PNG の中身が壊れている、手で編集された、といった「参照は正しいのに見た目がおかしい」場合のための手段。

アバターの見た目がおかしいときは「Hierarchy でアバターを右クリック → 修復」、それでも直らなければ「Inspector で再ベイク」という2段階を案内する。`help_packing` の文言にもこの手順を1文で加える。

アニメーションクリップの収集は VRCSDK フックの `CollectClips`（`SpecularExPackedMaskBuildHook.cs:43–62`）と似た処理になる。コアのエディタアセンブリには VRCSDK への依存がないため、Hierarchy からの修復では `Animator.runtimeAnimatorController` のクリップまでを集める。`VRCAvatarDescriptor` のレイヤーは VRCSDK アセンブリ側から収集関数を登録する形にする（登録がなければ Animator のみ）。最初の実装では Animator のみでもよい。アップロード時はビルドフックが全体を見るため。

## 4. v1 実装からの変更点

### 4.1 削除するもの

| 対象 | 箇所 | 理由 |
|---|---|---|
| 依存インデックス（`_containerDeps` / `_depContainers`、`RebuildIndex`、`SetIndexEntry`、`RemoveIndexEntry`、`IndexedContainers`、`MoveIndexPath`） | Watcher `73–77, 351–438` | 範囲外のマテリアルを探すための仕組み。v2 では監視セットの逆引き（`_byPath`）で足りる |
| 全件確認（`_fullCheckReason`、`CollectTrackedMaterials(null)` 経路） | Watcher `56–57, 227–250` | 状態を失った場合はシーン再走査で作り直す |
| `SessionState` への保存と復元（`SavedState`、`SaveState`、`LoadState`、`ApplyRestoredState`、`_restored`） | Watcher `506–645` | 3.3 のとおり、リロード後の再走査で状態を作り直せる |
| 自己保存の抑制（`SelfSave`、`NoteSelfSave`、`ForgetSelfSave`、`IsOwnSave`、`PurgeExpiredSelfSaves`） | Watcher `79–90, 155–193`、Store `211–215` | 3.2 のとおり、スロット比較だけで終わる |
| コンテナのインポートでの `GetDependencies` と `UsesSpecularExShader` 判定 | Watcher `278–291` | 監視セットにあるパスだけを扱う |
| 拡張子テーブル | Watcher `92–102` | パスの逆引きで判定するため不要 |

`UsesSpecularExShader` と `ShaderFolder`（E）は `Update All Materials` の走査で引き続き使うため Store に残す。

### 4.2 変更するもの

| 対象 | 変更 |
|---|---|
| `Tracked` | `active` / 保留のフラグと、マテリアル自身のアセットパスを持つ。`_byPath: Dictionary<string, HashSet<int>>` を追加し、`Track` / `Untrack` で更新する |
| `CollectSceneMaterials` | 3.3 の再走査に置き換える。アクティブ判定を加え、監視セットの整理（Untrack）も行う |
| `OnChangesPublished` | GameObject のプロパティ変更からアクティブ化を検出し、保留中のマテリアルを要求する |
| Postprocessor | 3.5 のとおり、パスの逆引きのみにする |
| `EditorSceneManager.sceneClosed`、`PrefabStage.prefabStageClosing` | 購読を追加し、シーン再走査を要求する（監視セットの整理のため） |
| `Store.UpdateAllMaterials` | `RebuildIndex` を使わず、`FindMaterialContainerPaths` と `UsesSpecularExShader` でマテリアルを集める（キャンセル可能な進捗表示は維持） |
| Inspector | 3.6 のステータス行と修復導線。言語ファイルにキーを追加する |

### 4.3 そのまま残すもの

- `RequestIfSlotsChanged` と `_slotState`（A）。ただし 3.1 の不変条件に従い、Untrack で消す
- `_verified` と `useCache`（H）。Untrack で消す
- `_verifiedImportSettings`（D）、`_shaderFolder`（E）、`_stateCache` とアセット世代（G）
- 計測マーカーとデバッグログ（M）。ログの項目は「監視セット数、保留数、アクティブ化で検証した数」に置き換える
- `Busy` 判定と、1回の `EditorApplication.update` でまとめて処理するスケジューリング

### 4.4 Process の骨格

```
Process():
    if Busy: return
    targets = drain(_materials)                    // 操作由来: 即時
    targets += dirty tracked (3.5)                 // テクスチャ・コンテナのイベント
    if _rescan: RescanScenes(targets)              // アクティブのみ targets に入る
    EnsureAll(targets, persist: true, useCache: true)
    for m in targets: _slotState[m] = SlotSnapshot(m); Track(m); _deferred.Remove(m)
    debug log
```

v1 の `Process`（Watcher `214–328`）にあった、影響先の確保と依存更新の順序制御、全件確認の分岐、自己保存の照合がなくなる。

## 6. 受け入れるトレードオフ

v2 で意図的に保証しなくなるもの。いずれもビルドフック・NDMF で最終的に正しくなり、修復導線で直せる。

1. **シーンにない `.mat` は、ソースを編集しても追従しない。** そのマテリアルをシーンに置く、Inspector で開く、修復・再ベイクを行う、のいずれかで直る。Inspector で開くと、監視セット外のマテリアルには `_slotState` がないため必ず検証される。
2. **ディスク上の `.mat` が古いパック参照のまま残ることがある。** 例: シーン外のプレハブのマテリアルを Git にコミットする、unitypackage で配布する。受け取った側でも、シーンに置いた時点・ビルド時点で直る。配布前の確認として `Update All Materials` を案内する（README / リリースノート）。
3. **非アクティブなオブジェクトは、アクティブ化のイベントが届かない経路で表示された場合に古いまま見えることがある。** 3.4 のとおり。
4. **アニメーションでのみ差し替えられるマテリアル**（どの Renderer にも付いていないもの）は監視セットに入らない。Animation ウィンドウのプレビューで古い状態が見えることがある。Hierarchy からの修復は Animator のクリップも対象にする（3.6）。
5. **追加ロードされていない（アンロード状態の）シーン** のマテリアルは対象外。

v1 で「ビルド時の修復だけを理由に、エディタでの更新漏れを許容しない」としていた前提（v1 1章）は、v2 では **シーン上のアクティブなマテリアルに限って** 維持する、と改める。

## 7. 実装の順番とコミット単位

1. v1 の計測（シナリオ 1〜6、8、9）を行い、基準値を記録する
2. `refactor(editor): 監視範囲をシーンと操作対象に限定し依存インデックスを撤去` — 4.1 の依存インデックス・全件確認・`SessionState`・コンテナ判定の削除、`_byPath` の導入、3.3 の再走査（まだ全マテリアルを即時検証）、`Update All Materials` の走査の置き換え
3. `refactor(editor): 自己保存による再パック抑制を撤去` — B の削除。自己保存の後に余分な検証が走らないこと（ログの `cached` 数）を確認する
4. `perf(editor): 非アクティブな Renderer のマテリアルの検証を保留` — `_deferred` とアクティブ化の検出
5. `feat(editor): パック状態の常時表示とワンクリック修復` — 3.6 の Inspector ステータス行、Hierarchy・Project の右クリック、メニュー、言語ファイル
6. 1 と同じシナリオを計測し、v1 との比較を本書に追記する
7. 回帰確認（8章）

2 は単独で動く状態にする（2 の時点で v1 より保証範囲が狭くなるが、ビルドの正しさは変わらない）。問題が出たときにコミット単位で戻せるようにする。

## 10. 実装状況（2026-09-27）

7章の手順 2〜5 を `develop` に実装した。3つのエディタアセンブリ（`SpecularExV2.Editor` / `.NDMF.Editor` / `.VRCSDK.Editor`）は `dotnet build` でコンパイルできることを確認している。**Unity 上での動作確認・計測（手順 1・6）と 8章のチェックリストは未実施。**

9章の決定事項は、すべて推奨どおりにした（アイドル時の検証なし、Inspector で開いたシーン外の `.mat` も再走査で監視から外す、ステータス行はバージョンバーの直下、Hierarchy からの修復は Animator のクリップまで、`Update All Materials` は残す）。

計画からの差分:

- **コミット単位:** 手順 2〜4（監視範囲の限定・自己保存抑制の撤去・非アクティブの保留）は Watcher の書き直しとして1つのコミットにまとめた。修復メニュー（3.6 のうち Hierarchy・Project・シーンのメニュー）も Watcher に置いたため同じコミットに含む。Inspector と言語ファイルは別のコミット。
- **再走査のトリガー追加:** Play モードの開始・終了（`playModeStateChanged`）と、監視中のマテリアルが破棄されていた場合（モデルの再インポートでマテリアルが作り直された場合など）にも再走査する。これにより v1 の既知の制約（Play モード終了後のシーン埋め込みマテリアル）も解消する見込み。
- **生成マスクのインポート:** 自分の書き込みでも毎回届くため、要求はせず H の無効化だけにした（v1 と同じ）。生成マスクの削除と移動は要求する。
- **修復（Repair）:** 対象マテリアルの H だけを無効化し、`useCache: true` で `EnsureAll` を呼ぶ。D（インポート設定）のキャッシュは、生成ファイルのインポート・削除・移動のたびに無効化されるため信用する。結果は H に記録され、監視セットにも登録される。再ベイクは従来どおり `rebake: true`。
- **Inspector:** 折りたたみ内の再ベイクボタンは削除し、ステータス行のボタンに移した。ステータス行は「更新待ち」のときだけ警告色にする（「保存されていないテクスチャを含む」はビルド時にベイクされる正常な状態のため）。言語キー `btn_rebuild_packed_mask` は `label_packed_masks` / `btn_rebake` / `tooltip_rebake` に置き換えた。
- `Store.InvalidateAllCaches()` は使われなくなったため削除した。`Store.InvalidateVerified(int)` を追加した（破棄されたマテリアルの記録を消すため）。

## 11. 追加: マスクを設定したときの操作ブロックの削減（2026-09-27）

マスク画像をスロットに設定すると、約3秒エディタが固まる問題への対策。アセットの取り込み（テクスチャ圧縮）は Unity の仕様でメインスレッドを止めるため、完全なバックグラウンド化はできない。そのため、取り込み以外の処理をメインスレッドから外し、取り込み自体も1回に減らした。

1. **取り込みを1回にする（`Store.PrepareMeta`）**
   - 新しい生成ファイルを書く前に、設定が正しいことを確認済みの既存生成ファイルの `.meta` をテンプレートとして書く（guid だけ新しく生成）。これで最初の取り込みから BC7 などの最終設定になる。
   - 従来は、既定の設定で取り込んだあと、BC7 に変えてもう一度取り込んでいた。
   - `.meta` の形式は Unity 自身が書いたものをそのまま使い、guid の行以外には触れない。テンプレートがない場合（プロジェクトで最初の1枚）と、設定が一致しなかった場合は、`EnsureImportSettings` が従来どおり直す。
2. **ベイクをバックグラウンドで行う（`Store.StartBake`、Watcher の自動確認のみ）**
   - メインスレッドでは GPU での描画（`MaskPacker.RenderPack`）と `AsyncGPUReadback` の要求だけを行う。
   - 読み戻しが終わったら、ワーカースレッドで PNG へのエンコード（`ImageConversion.EncodeArrayToPNG`）と `Temp/SpecularExV2Bakes` への書き込みを行う。
   - 完成したファイルは、メインスレッドでコンパイル中・取り込み中でないときに、`.meta` と一緒に所定の場所へ移動し、まとめて取り込む。そのあと `BakesImported` で待っていたマテリアルを Watcher に戻し、通常の確認で割り当てる。
   - ベイク中のマテリアルは以前のパック済みテクスチャのままで、状態は「更新待ち」になる。検証済みとしては記録しない。
   - 同じファイルを必要とするマテリアルは同じベイクを待つ。失敗はログに出すだけで再試行しない（次の変更か手動修復で直る）。ドメインリロードで進行中のベイクは破棄され、再走査で要求し直される。
   - `AsyncGPUReadback` が使えない環境では従来どおり同期でベイクする。
   - 修復・再ベイク、`Update All Materials`、ビルドは同期のまま（結果をその場で必要とするため）。
3. **デバッグログ**: Watcher のログに `background`（バックグラウンドに回したパック数）を追加した。取り込み完了時には、メインスレッドでかかった時間（`Store.LastBakeImportMs`）を出す。

- [ ] 2枚目以降の生成ファイルが1回だけ取り込まれる（ログの `reimported` が 0）
- [ ] バックグラウンドで作ったマスクの上下が反転していない（`AsyncGPUReadback` と `ReadPixels` の行の並びが一致する）

- [ ] ベイク中にスクリプトを再コンパイルしても、再走査で作り直される
