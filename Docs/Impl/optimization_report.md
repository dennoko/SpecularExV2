# SpecularExV2 最適化調査レポート

調査日: 2026-09-26  
対象リビジョン: `3ed930c`  
確認環境: Unity `2022.3.22f1` / ローカル導入済み lilToon `2.3.4`

## 1. 結論と調査範囲

最適化できる候補はある。まずは **強度0での処理省略、初期値で不要な演算の省略、同じUVでのマスク読み取り共有** を検証する価値が高い。次に、追加法線を使わない構成の接線入力削減、パック画像の解像度調整を検討する。

本調査は `Shaders/custom.hlsl`、`custom_insert.hlsl`、プロパティ／コンテナ定義、マスク生成・監視・ビルドフック・Inspector、および導入済み lilToon のフック展開箇所を静的に確認したもの。シェーダーやEditorコードは変更していない。GPU計測、生成シェーダーの逆アセンブル、Unityでのコンパイル・描画比較、アップロード後の容量測定は実施していない。以下の効果は候補またはソースから数えた値であり、FPSやGPU時間の改善を保証するものではない。

主に Built-in Render Pipeline の通常Forwardパスを評価した。コンテナはURP/HDRPも参照するが、追加ライトの扱いを含め、これらへの効果・互換性は未検証。対象ディレクトリ内に評価用 `.mat` / `.unity` / `.anim` はなく、実際に多用される設定の頻度は未調査。

| 優先度 | 候補 | 主な対象 | 削減の見込み | 注意点 |
|---|---|---|---|---|
| P1 | 強度0のレイヤーを省略 | GPU | 該当レイヤーのサンプルと演算 | 法線は完全な同値性に注意 |
| P1 | 初期値・端点専用の経路 | GPU | `pow`、回転、反射、正規化 | 分岐追加が実際に有利か確認 |
| P1 | 同一UVのマスク・ノイズ共有 | GPU | 条件成立時に複数サンプルを削減 | UV一致・レジスター寿命・フック差 |
| P2 | 追加法線なし構成のTBN削減 | GPU / ビルド | 接線補間・TBN関連処理 | 静的な構成分離が必要 |
| P2 | パック解像度と縦横サイズの調整 | VRAM / 転送 / ビルド | 画像面積を削減 | 画質、再生成キー、アニメーション |
| P2 | 元マスクのビルド依存を確認 | 配布サイズ / VRAM | 二重収録している場合に削減 | 現状で二重収録するかは未確認 |
| P2 | ForwardAddの利用範囲を見直す | GPU | 追加ライトごとの処理 | 表現変更。既存設定の利用を優先 |
| P3 | 法線2層の座標変換を統合 | GPU | 行列積・正規化 | 現行と同値とは限らない |
| P3 | Editorの依存検索・ハッシュ共有 | Editor CPU | 大規模プロジェクトの待ち時間 | GPU描画性能には影響しない |

P1は着手順の推奨であり、実測済みの速度順位ではない。

## 2. すでに実装されている対策

- 拡張用テクスチャは、RGBAマスク2枚、追加法線2枚、MatCap1枚の計5宣言。マスクを8枚個別に宣言する構成ではない。共有サンプラーも利用している（`custom.hlsl:129–151`）。ただし、**テクスチャ宣言数の削減とサンプル命令数の削減は別**。
- 7機能の有効フラグでレイヤーを分岐し、ノイズ強度0ではノイズを読む経路を通らない記述になっている。これらはマテリアル値による分岐であり、生成GPUコードでの分岐・平坦化は未確認。
- MatCapは方向を補間してから1回だけテクスチャを読む。2画像をクロスフェードする構成ではない。HSVGの中立値も既に早期returnしている（`custom_insert.hlsl:60,202`）。
- 追加法線2層の後に派生値をまとめて再計算している。リムは通常ForwardAddでは展開されず、Metaでも明示的に除外している。
- パック画像には圧縮、ミップマップ、ストリーミング設定、Read/Write無効化が実装済み。PCはBC7、Android/iPhoneはASTC 6×6（`SpecularExPackedMaskStore.cs:256–334`）。
- パック生成は入力ハッシュによる共有・再利用、インポートのまとめ処理、変更時のみ保存を行う。毎フレームGPUでパックし直す構成ではない。
- 拡張ソースに独自の `shader_feature` / `multi_compile` 宣言は見当たらない。現在の機能トグルだけで7機能分の組合せバリアントが増えるわけではない。

## 3. サンプル数の静的な見積もり

通常Forwardの拡張部分のみを数える。lilToon本体の読み取り、影、反射プローブなどは含めない。「ノイズあり」は該当する全レイヤーでノイズ強度が正の場合。

| 有効機能 | 基本サンプル数 | ノイズ追加 | ForwardAdd |
|---|---:|---:|---|
| Normal 3rd / 4th | 各2（法線＋マスク） | 0 | 同じ処理が展開される |
| Specular 2nd / 3rd | 各1（マスク） | 各1 | `ApplyFA` が有効な層のみ |
| World MatCap | 2（MatCap＋マスク） | 1 | 展開される |
| Rim 2nd / 3rd | 各1（マスク） | 各1 | 通常ForwardAddでは展開されない |
| 全7機能・ForwardBase | **10** | **+5 = 15** | — |
| 全機能・ForwardAdd 1回、両SpecularのApplyFA有効 | **8** | **+3 = 11** | 追加ライトの実描画パス数に依存 |

これはソース上のサンプリング呼出回数。GPUのメモリアクセス回数、コンパイラー最適化後の命令数、実時間ではない。テクスチャキャッシュのヒット率などによって負荷は変わる。

根拠: `custom.hlsl:196–333` と lilToon `lil_pass_forward_normal.hlsl:333,521,540,553–555`。Lite/Gemでは展開されるフックが異なるため、この表をそのまま適用しない。

## 4. 優先候補の詳細

### 4.1 強度0のレイヤーをGPU側で省略する（P1）

**現状:** `custom.hlsl:213,234,272,301` の入口は主に `Enabled` だけを確認する。Inspectorの `SyncAllEffective` もUIトグルと必要テクスチャの有無を見ており、強度0を除外していない（`SpecularExV2Inspector.cs:337–385`）。有効にしたまま強度を0へアニメーションさせる場合も、レイヤー内の処理が残る。

**提案:** 有限で正常な入力を前提に、Specularは `Strength != 0`、MatCapは `Alpha != 0` かつ色のalphaが0でないこと、Rimは `Strength != 0` かつ色のalphaが0でないことを、サンプリング前のマテリアル一様条件に加える。各層で基本1〜2サンプルと、使用中ならノイズ1サンプル、および演算を省略できる候補になる。色のRGBが黒という条件だけでは省略しない。Normal/Multiply合成では黒も結果を変える。

**互換性:** Inspectorで有効フラグを書き換える方式では、強度を実行時に戻しても復帰しない危険がある。現在の強度をGPU側で判定する方針を優先する。SpecularのClearCoatも `strength * mask` を使うので強度0なら減衰しないが、`EnableLighting == 0` や光色が黒という理由で層全体を省略すると、残るコート減衰を失う。

**法線は別扱い:** `NormalStrength == 0` でも、現状はTBNへの往復変換と正規化が走る。補間TBNが正規直交でない場合、これを省略すると完全に同じ結果にはならない。負の強度は有効なので `> 0` で判定してはいけない。法線の0強度省略は4.8と併せて視覚検証する。

**確認:** 強度0/微小値/通常値、0→1のアニメーション、全ブレンドモード、ClearCoatを比較する。分岐が残り、実際にサンプルが省略されたか生成コードでも確認する。

### 4.2 初期値・端点に軽い経路を設ける（P1）

| 箇所 | 現状 | 提案と条件 |
|---|---|---|
| `custom_insert.hlsl:53` FresnelWeight | Fresnel強度の初期値0でも可変指数の`pow`を記述 | 強度0なら1を返す経路を比較 |
| `custom_insert.hlsl:143` SpecularLightDir | FakeLightBlend初期値0でも仮想光方向の構築とSafeNormalizeを2回記述 | blendが0なら仮想光を構築しない。ただし現状のL再正規化の扱いを保つ／単位長を確認 |
| `custom.hlsl:272` MatCap | WorldFixed初期値0でも反射、yaw回転、両方向の構築を記述 | `saturate(WorldFixed)==0` はビュー方向だけ、1はワールド方向だけを作る。中間値は現状維持 |
| `custom.hlsl:160` yaw回転 | 角度0でも`sincos`を記述 | 0度では回転を省略。MatCapのビュー端点では回転経路全体を不要にする |
| `custom.hlsl:196` 追加法線UV | ScrollRotateが全0でも回転対応の`lilCalcUV`を呼ぶ | 全0ならSTのみのオーバーロードを使う経路を比較 |
| 同上 距離フェード | fade.z初期値0でも距離・除算・saturateを記述 | フェード無効時の係数を1にする経路を比較 |

**効果の確度:** 不要な式がソースにあることは確認済みだが、ドライバー／コンパイラーが既に省略している可能性もある。短い式のために分岐を増やすと逆効果になり得るため、まずMatCapとFakeLightのまとまった演算を優先する。一般に分岐方法に万能な選択肢はなく、実行時変更の必要性も考慮する。[Unity: Conditionals in shaders](https://docs.unity3d.com/2022.3/Documentation/Manual/shader-conditionals.html)

**見た目:** MatCap端点でも現行のSafeNormalizeを必要に応じて残す。単に `fd.uvMat` へ置き換えると、NormalStrengthや通常MatCap側の法線変更を無視する可能性がある。旧マテリアルのWorldFixed=2は現在と同じく1として扱う。

### 4.3 同一UVのパックマスクとノイズを共有する（P1）

**現状:** `DNKW_SAMPLE_MASK` / `DNKW_SAMPLE_MASK2` はチャンネルごとに独立STを受け、各フックでサンプリングする（`custom.hlsl:150–157`）。デフォルトSTは一致するが、異なるプロパティなのでマテリアル値の一致をコンパイラーが常に知るとは限らない。

**提案:** 同一テクスチャ・同一UV・同一サンプラー・同一LOD/微分条件の組だけ、取得したfloat4を再利用する。例えばPack1を1回読みR/G/B/Aを共有し、Pack2のRGBとノイズAも共有する。STが異なる場合は従来の読み取りへ戻す。まず同一フック内やノイズ共有など小さい範囲で評価し、フックをまたぐ共有は後から試す。

**上限の目安:** 全7機能が有効で、全マスク・全ノイズのSTと実際のUVが一致し、安全に共有できる通常ForwardBaseでは、パック2回＋法線2回＋MatCap1回の **計5回** までソース上の読み取りをまとめられる見込み。現状の10回（ノイズなし）／15回（全ノイズあり）に対し5回／10回分の削減候補。ただし実測の高速化率ではなく、部分的に有効な設定では利得も小さい。

**実装条件:** フック間でUVが変化していないことを確認し、Lite/Gemなどフック構成が違うパスでも未初期化値や未宣言変数が出ないよう設計する。全機能OFFなのにキャッシュ用の2サンプルを無条件で増やしてはいけない。長時間保持するfloat4やST比較のコストによりレジスター負荷が増えるため、サンプル数と一緒に計測する。STがアニメーションする場合、Editorで一度だけ作った「一致」フラグには依存しない。

### 4.4 追加法線を使わない構成からTBN関連処理を外す（P2）

**現状:** `custom_insert.hlsl:21–26` で `LIL_V2F_FORCE_TANGENT` と `LIL_REQUIRE_APP_TANGENT` を無条件に定義している。通常パスは前者により `tangentWS : TEXCOORD5` を宣言する（lilToon `lil_pass_forward_normal.hlsl:62–93`）。法線機能OFFの一様分岐だけでは、頂点入力・補間の構成をコンパイル時に除けない。

**提案:** 「追加法線3rd/4thを使う可能性があるか」を静的に分離する小数の構成を試す。本体の法線、異方性、パララックスなどがTBNを必要とする場合は残す。拡張の実行時ON/OFFやアニメーションがあるマテリアルもTBNありを使う。

**注意:** ローカルlilToon 2.3.4には `LIL_V2F_FORCE_BITANGENT` の参照が見当たらず、bitangentは `cross(normalWS,tangentWS)` でフラグメント側に構築される（`lil_common_macro.hlsl:2323`）。この未使用defineを削除するだけで補間スロットが1つ減るとはいえない。

7機能を個別に2状態の静的キーワードへ変えると、理論上は既存の組合せに最大 `2^7 = 128` 倍の軸を追加する。実際の残存数はストリッピング等に依存する。最初は法線有無の1軸に絞り、必要バリアントの保持とビルド時間を評価する。バリアント数がキーワード集合の組合せで増える点はUnity公式の説明にもある。[Unity: Shader variants](https://docs.unity3d.com/2022.3/Documentation/Manual/shader-variants.html)

### 4.5 パック画像の解像度と縦横サイズを選べるようにする（P2）

**現状:** `SpecularExMaskPacker.cs:127–134` は入力の最大の幅または高さを取り、2の累乗の正方形へ統一して最大2048にする。例えば2048×256の入力1枚でも2048×2048のパックを生成する。他チャンネルの小さなマスクも同じ面積になる。

**提案:** 幅・高さを別々に決定する方式や、パックごとの最大解像度設定を追加する。2048四方から1024四方へ変えれば基底レベルの画素数は1/4になる。VRAM・転送量の効果は圧縮形式、ミップ常駐量、入力構成に依存する。

**条件:** 長方形化・低解像度化はサンプリングとミップの選択に影響し得るため、細い境界とノイズの画質を比較する。生成仕様を変更したら `SpecularExMaskPacker.Version` を更新し、設定値も入力キーへ含めて古いパックが再利用されないようにする。Inspectorで一時OFFというだけで入力を削ると、後のアニメーションONで欠落するため、未使用チャンネルの除外は実行時不使用を保証できる場合だけにする。圧縮・ミップ・Read/Write設定は既に実装されており、改めて有効化する提案ではない。

### 4.6 元マスクがビルドにも残るかを確認する（P2・要計測）

**現状:** 元の単チャンネルマスクはプロパティとして残り、Editorはそれを生成元として使う。ビルドフックの `OnPreprocessAvatar` はパック生成・割当を行うが、元スロットの参照を除去する処理はない。ランタイムHLSLの拡張テクスチャ宣言はパック側のみである。

**提案:** まずビルド成果物の依存テクスチャ一覧・容量で、元画像とパックの両方が収録されるか確認する。二重収録する場合に限り、最終パック生成後のビルド用マテリアル複製から元スロット参照を外す方法を検討する。

**条件:** 編集用 `.mat` の元参照は保持し、元画像を別機能が使うケースや、後段ツールが再パックするケースも考慮する。ビルド処理順序の確認が必要。参照が残るというソース上の事実だけから、実際の二重収録やVRAM常駐を断定しない。

### 4.7 ForwardAddごとの反復負荷を管理する（P2）

**現状:** 通常ForwardAddには追加法線、許可されたSpecular、World MatCapが展開される。追加法線は後段のlilToon本体のライティングにも影響するため、追加SpecularのApplyFAがOFFでも無条件には省略できない。

**提案:** 追加光源のハイライトが不要な用途は既存の `Refl2nd/3rdApplyFA` をOFFにする。必要ならMatCapにも任意のForwardAdd適用設定を追加するが、現行互換の初期値にする。強度0経路やマスク共有はこのパスでも評価する。

**注意:** 機能をOFFにしてもForwardAddの描画パス自体が消えるとは限らない。MatCapのMultiplyなどは合成先へ影響するため、照明係数0だけを理由に省略しない。追加ライト数を固定して差分を測定し、透過・両面のオーバードローも分けて調べる。描画方式を変える案は見た目の変更を伴うため、一律には適用しない。

### 4.8 追加法線2層の変換統合は慎重に扱う（P3）

**現状:** `DNKW_NORMAL_LAYER` は1層ごとに `mul(fd.TBN, fd.N)` → Whiteout blend → `normalize(mul(..., fd.TBN))` を行う（`custom.hlsl:196–210`）。2層有効ならTS/WSの往復と正規化を2回行う。

**候補:** 接空間へ1回変換し、2層のWhiteoutを順に適用し、最後に1回だけWSへ戻す。関連計算の削減余地はあるが、単純な置換は推奨しない。

**理由:** lilToonのWhiteoutは `float3(dst.xy + src.xy, dst.z * src.z)`（`lil_common_functions.hlsl:135`）。途中でdstを正規化すると、次の層のxy加算における相対的な大きさも変わる。また補間TBNは正規直交を保証しないので、行列と転置を往復しても完全な恒等変換にはならない。層間正規化を維持してもTBN往復削除が同値とは限らない。非一様スケール、ミラーUV、滑らかな曲面、強い法線、負の強度、裏面で差分を確認し、必要なら任意の軽量モードとする。

### 4.9 Editorの再検索・ハッシュ計算を減らす（P3）

**現状:** `SpecularExPackedMaskWatcher.CollectAffectedAssetMaterials`（177行付近）はテクスチャ変更時に全マテリアルコンテナを列挙し、依存関係を照合する。`SpecularExPackedMaskStore.InputKey`（210行付近）は各入力の依存ハッシュを取得する。同じマスクを大量のマテリアルが共有する場合、再ベイク不要でも検索・ハッシュ計算が重複する。

**提案:** まず1回の `EnsureAll` 呼出内で入力パスごとの依存ハッシュを共有する。さらに実測で必要なら、元テクスチャ→対象マテリアルの逆引きを保持する。画像更新、移動、削除、マテリアル変更、ドメインリロードでの無効化を設計し、ビルド時の全対象整合チェックは残す。

**補足:** `BakePng` はGPU Blit後に `ReadPixels`、`Apply`、PNGエンコードを行うが、キャッシュミス時のEditor処理である。GPU readbackの非同期化などは変更規模に対する効果が不明なため、最初は呼出回数と依存検索時間を測る。ゲーム中のシェーダー速度改善とは分けて扱う。

## 5. そのまま適用しない方がよい変更

- **全floatのhalf化:** 高smoothnessのGGXでは小さい分母と大きな値を扱う。`roughness` 下限0.002、`r2`、`1e-7`等を含む計算の精度を落とすと破綻し得る。HDR色も含め、型変更は対象を限定して実機で判断する。
- **マスク0や距離フェード0の画素だけテクスチャ読み取りを飛ばす:** 一様なマテリアル分岐とは異なり、画素間で分岐が分かれる。暗黙微分のサンプルやリムの `fwidth` の周辺へ安易に分岐を導入しない。HLSLのbranch属性には微分を含む処理との制約もある。[Microsoft: HLSL if statement](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-if)
- **MatCapを暗黙LODへ変更:** 現在の明示LODはワールド反射の折返し境界とユーザーのBlur指定に関わる。サンプル種類だけを変える案は視覚仕様も変える。
- **法線派生値の更新削除:** `reflectionN`、`matcapN`、`ln`、`nv`などは後段で利用される。追加法線が反射や影へ反映されなくなる。コンパイラーが未使用値を除去する可能性もあるため、生成コードで必要性を判断する。
- **全機能の静的キーワード化、コンテナの一括削除:** バリアント増加、実行時アニメーション、既存マテリアルやUsePass依存を検証してから判断する。コンテナのファイル数はGPU負荷やコンパイル済みバリアント数そのものではない。
- **既存の共通式を手で共有するだけの変更:** `dot(N,V)`等はインライン化・共通式除去で既に共有される可能性がある。Specular2層は法線強度やFakeLightの設定も別なので、無条件には共有できない。

## 6. 実装する場合の検証手順と採用条件

### 6.1 基準と比較条件

1. 現行版と変更版を別マテリアルで用意し、同一メッシュ、画面占有率、照明、カメラ、描画解像度で比較する。機能全OFF、各機能単独、全機能ON、ノイズ全ONを揃える。
2. 最初はOpaque・通常Forwardで調べ、次に追加ライト0/1/複数、Transparent、両面、アウトライン、Tessellation、Multi、Lite/Gemなど使用対象を確認する。未使用の特殊パスまで同じ効果を仮定しない。
3. P1を1項目ずつ適用し、シェーダーのウォームアップ後に複数回A/Bを交互に測る。VSyncやCPU律速でFPSが頭打ちになる場合は、GPU時間を比較する。

### 6.2 記録する値

| 対象 | 指標 | 判定 |
|---|---|---|
| GPU | 対象draw/passの時間、フレームGPU時間、サンプル命令、ALU、レジスター情報（取得可能な範囲） | 実行時間の差が測定のばらつきを超える |
| CPU / Editor | 画像更新から完了まで、EnsureAll、依存探索、ReadPixels、エンコード、インポート時間 | 入力変更時の待ち時間と割当を削減 |
| ビルド | 残存バリアント数、初回/再ビルド時間、容量 | GPU利得に対し増加が許容できる |
| テクスチャ | 生成解像度、圧縮形式、実常駐量、元画像の依存 | 重複・過剰解像度を実際に削減 |

Frame Debuggerでパス数を確認し、UnityのGPU計測や対応するGPUキャプチャで実時間・生成コードを確認する。独立した評価環境での計測と実アバターでの計測を両方行う。

### 6.3 見た目の回帰項目

- Specular: GGX/Blinn-Phong、smoothness最大付近、ClearCoat、FakeLightの0/中間/1、暗い環境、ForwardAdd。
- MatCap: WorldFixedの0/中間/1/旧値2、回転0/非0、各合成、HSVG中立/非中立、HDR、Blur、折返し境界、裏面、VR両眼。
- Normal: 1層/2層、強度-2/0/2、距離フェード、UV0〜3、スクロール・回転、ミラーUV、非一様スケール。
- Mask/Rim: 同一ST/異なるST/アニメーションST、全白/全黒/細い境界、ノイズ、リムの硬い境界と各合成。
- 運用: 既存マテリアル、Undo、複数選択、ビルド時生成マテリアル、アニメーションでの有効化、Meta/ShadowCasterの出力維持。

**採用順:** P1の強度0省略と端点経路を小さく実装・比較し、次にマスク共有を評価する。そこで十分な効果が得られない場合にTBNの静的分離や画像サイズの変更へ進む。見た目が変わる法線統合は独立した変更として判断する。
